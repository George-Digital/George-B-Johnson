# Write the operating SOP

**An operating SOP makes the common path repeatable without hiding the decisions, sources, exceptions, and human approvals that keep it safe.**

I write an SOP after I can describe the system in the language of real work. I do not write it as a technical monument or as a transcript of every past experiment. The operating SOP tells a capable person how to start, prepare approved inputs, run the current process, review the result, record what happened, and route exceptions.

I begin with scope. I state the trigger that starts the SOP, the user it serves, and the output it prepares. I also state exclusions. A clear exclusion protects a user from applying a common-path instruction to a case with different rules, elevated privacy needs, or a consequential decision. If the system cannot handle the case, the SOP should make the next human destination easier to find than an improvised workaround.

I make every step observable. “Use good judgment” is not a usable instruction on its own. I write what to check, which approved source to use, what a complete input looks like, and what the operator should record. I distinguish a mechanical step from a judgment step. For example, an operator may run a summary template, while a manager decides whether the proposed priority is appropriate. The SOP names both without pretending the template has the manager’s authority.

Current sources matter. I identify the approved policy, knowledge base, form, or data location and who owns it. When sources disagree or look stale, the operator does not choose the convenient answer. They pause, preserve a safe reference, and route the question to the source owner. I also state the privacy boundary: which data is allowed in the workflow, which data requires approved access, and what must be removed, anonymized, or handled through another process.

I write the review gate with the same care as the run step. Who reviews? What do they inspect? What makes the output ready to use, ready to revise, or inappropriate to use? The answer can be a short rubric, but it must be concrete enough that a new reviewer can see the difference. The final decision remains with the person or role authorized to make it.

I include the evidence trail that is proportionate to the work. A low-risk drafting workflow may only need a version, an input reference, and a note on revisions. A more consequential workflow may need an approved record in its authorized system. I never ask a user to copy confidential inputs into a casual log merely to prove they followed the SOP. The record should support audit, learning, and handoff without expanding exposure.

I test the SOP by giving it to someone who did not write it. I ask them to follow a safe common case and explain where they hesitated. Their confusion is useful evidence. I revise the wording, source link, step order, or exception route before treating the SOP as the current operating version.

## Concrete example

I write an SOP for a procurement-request brief. The trigger is a complete request in the approved intake form. The operator checks amount, delivery date, and business owner; uses the current supplier policy; runs the brief template; and labels any missing field. A procurement lead reviews budget category and exception flags before the brief moves forward. Requests containing personal banking details or a policy conflict leave the workflow and go to the authorized procurement process. The log stores the request reference, SOP version, reviewer decision, and any change request, not copied sensitive data.

## Action checklist

- Define the SOP trigger, user, output, and exclusions.
- Write the common path as observable actions in the order they occur.
- Name the approved sources and the response to a conflict or stale source.
- Separate automated assistance from human judgment and approval.
- State the input, privacy, and access boundaries.
- Add review, recordkeeping, stop, and escalation steps.

## Required deliverable

Create a **Current Operating SOP** with scope, common-path steps, source authority, input checks, AI-assisted step, human-review gate, recordkeeping method, privacy boundary, exceptions, escalation contacts, and a safe test of the instructions by another person.
