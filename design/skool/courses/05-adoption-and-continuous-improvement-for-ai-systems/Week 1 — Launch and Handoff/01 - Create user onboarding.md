# Create user onboarding

**Good onboarding lets a new operator recognize the right use case, run the common path, review the result, and know when to stop.**

I design onboarding for the moment someone needs to use the system, not for a long tour of every feature or prompt detail. A new user should quickly understand what the workflow is for, when it fits, where to find the approved version, and what remains their responsibility. If that cannot be explained plainly, the operating process is not ready to hand off.

I start with a short answer-first orientation: this system helps with this recurring situation, uses these approved inputs, produces this draft or structured output, and requires this human check before the next action. I put that answer where the user will see it at the point of use. I do not expect them to remember a launch meeting or hunt through chat for an old link.

Then I teach the common path through one safe example. I show the trigger, the approved input location, the pre-run check, the action to take, the output to inspect, and the handoff. I include the result of a missing or conflicting input. People need to see that a pause or a request for clarification is a correct outcome, not a failure to work around. For a system that touches sensitive information, I explicitly show what must not be entered and where the approved secure process begins.

I keep the first use bounded. I may ask a new operator to run one low-risk case with a reviewer nearby or to compare the draft with their existing manual method. I do not ask them to abandon a trusted fallback after one demonstration. The goal is informed use, not forced compliance. If someone needs accessibility support, translation, different timing, or an alternative format, I treat that as part of the onboarding design.

I separate user instructions from owner instructions. Users need the steps and boundaries that apply to their work. The operating owner needs to know how to answer recurring questions, collect feedback, and correct or pause the process. A reviewer needs the quality checks and authority boundary. Sending everyone the full technical history often obscures the action they need to take.

I use questions to check understanding, but I avoid turning onboarding into a test of loyalty. I ask a user to identify a good use case, name the human-review point, and explain what they would do with missing information. Their answer helps me find an unclear instruction or a condition the workflow does not meet. It also gives users permission to say that the process does not fit a real case.

Finally, I keep onboarding current. The owner notes the current version and source date, and updates the orientation when a material change affects the common path, privacy boundary, or review step. A short current guide is more valuable than an elaborate recording that describes a retired workflow.

## Concrete example

For a team meeting-brief workflow, I make a one-page onboarding guide for account coordinators. It opens by saying the workflow drafts a brief from approved meeting notes; it does not decide commitments or send client messages. The common-path example shows how to select an approved note, remove unneeded personal details, run the template, check the action-owner section, and send the draft to the account lead. A second example shows a missing decision owner and instructs the coordinator to request clarification rather than infer one. The owner observes each pilot user’s first run and records where the guide was unclear.

## Action checklist

- Write the purpose, fit condition, input boundary, output, and human-review point in plain language.
- Create one safe common-path example and one stop or clarification example.
- State where users find the approved current instructions.
- Define the first supervised or low-risk use.
- Provide an accessible or alternative route where the work requires it.
- Ask users how they would handle a missing input or uncertain output.

## Required deliverable

Create a **User Onboarding Guide** containing the answer-first orientation, common-path steps, approved input and privacy boundary, review check, stop or escalation route, safe examples, first-use plan, and a method for recording onboarding questions.
