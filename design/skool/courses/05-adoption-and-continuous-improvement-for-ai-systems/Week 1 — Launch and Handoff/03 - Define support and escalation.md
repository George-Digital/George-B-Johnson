# Define support and escalation

**Support is useful when users know where to bring a question, what evidence to include, and when an issue must stop the normal workflow.**

I do not launch a system with “message me if anything goes wrong” as the support plan. That phrase creates a private queue, hides recurring problems, and gives users no sense of what needs urgent attention. Instead, I define a small support route that matches the system’s risk, volume, and available operating capacity.

I separate routine support from escalation. Routine support includes a confusing instruction, an access problem, a missing field, an output that needs revision, or a suggestion for the next version. The operating owner or a named support contact can usually resolve these within the normal review cycle. An escalation is different: a privacy concern, an unauthorized access issue, a source conflict affecting a consequential outcome, a repeated quality failure, a suspected harmful output, or an incident that requires the process to pause. I make the distinction visible so users do not wait for a weekly review when the normal path is unsafe.

For each route, I state what the user should include. A useful support request has the system name and current version, the safe case or approved reference, what they expected, what happened, the work impact, and whether the process is paused. I do not request credentials, confidential records, or personal data in a shared community or general support channel. When sensitive evidence is necessary, I point users to the authorized secure channel and limit access to the people who need it.

I also name response expectations without promising constant availability. For example, a low-risk workflow can have a scheduled review window and a documented manual fallback. A safety, privacy, or authorization concern uses the organization’s urgent route. The key is that a user can tell which path applies and what to do while waiting. If there is no staffed urgent route, I say that plainly and require the system to stop rather than improvising an urgent response.

I give the operating owner an issue log. The log does not need to be complex: date, category, safe reference, impact, owner, next action, and resolution or decision. Patterns matter more than isolated complaints. Three people asking the same onboarding question may mean the guide is weak. Several outputs failing a quality check may mean the source, prompt, or scope needs review. The owner brings these patterns to the review cadence rather than closing tickets one by one without learning.

I protect users who report problems. A support plan should make it safe to say “I do not trust this output” or “this case does not fit.” That feedback is evidence, not a failure of the user. I also preserve the manual process for cases that need it. The existence of a fallback keeps a support request from becoming pressure to use an uncertain system.

The simplest check is practical: can a new user name the routine channel, the escalation route, the information to include, and the fallback? If not, I revise the support instructions before expanding access.

## Concrete example

For an AI-assisted incident-note draft, routine questions go to the operations owner in a scheduled daily support thread with a sanitized case reference and the output section that failed. A suspected privacy exposure, a safety issue, or an output that could affect a disciplinary decision is not posted there. The user stops the draft workflow, follows the organization’s incident route, and notifies the authorized manager. The manual incident-note process remains available while the owner reviews the event. The issue log later distinguishes an instruction problem from an incident that needs formal handling.

## Action checklist

- Separate routine questions, change requests, and stop-level escalations.
- Name the owner and authorized channel for each route.
- Specify the safe evidence a user should include in a support request.
- State what data must not be placed in a general support channel.
- Define the manual fallback while a question or issue is reviewed.
- Create a simple issue log and review recurring patterns.

## Required deliverable

Create a **Support and Escalation Plan** with issue categories, routine support route, escalation triggers, authorized contacts and channels, safe evidence requirements, an **Expected review window or event** for every row, manual fallback, privacy handling, and an issue-log format. Use only an owner-approved review cadence or event trigger; do not promise a response time that the responsible owner has not approved.
