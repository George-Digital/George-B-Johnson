# Week 2: Keep the context pack current, bounded, and usable

**Embed on:** `Week 2 — Maintain Trustworthy Knowledge/01 - Design a usable knowledge structure.md`

**Estimated recording time:** 8–9 minutes

**Outcome:** Members will make a usable working view with source references, ownership and expiration rules, role-based access boundaries, and explicit responses for missing, stale, conflicting, and access-limited context.

## What to demonstrate on screen

Use only the **Northstar Neighborhood Center volunteer shift-brief workflow — SYNTHETIC TRAINING EXAMPLE.** Do not open real drives or records. Keep the screen share free of notifications, account names, credentials, personal data, or confidential source text.

1. Show a synthetic Context Pack Version 1 outline with: `Start Here and scope`, `Source map`, `Current event facts`, `Approved operating rules`, `Examples only`, `Decisions and exceptions`, `Review needed`, and `Change log`. Each item contains a safe source reference rather than copied restricted material.
2. Open `Resources/Knowledge Update and Access Policy Template.md`. Show the distinct roles for pack owner, source owner, operational reviewer, and backup escalation owner, plus status labels, update triggers, expiration rule, change record, access matrix, and permission-uncertainty rule.
3. Populate a synthetic access-matrix row: `Current event facts`—view/run: coordinator; edit: event lead; approve change/share final brief: event lead; approved location: `Northstar scheduling system — synthetic reference`. Explain that the row records a boundary but does not grant access.
4. Show two synthetic maintenance events: a temporary rain-plan decision changes to `Expired` after its end date; a proposed safety-procedure update stays `Pending review` until the safety lead approves it and a relevant test is rerun.
5. Show a simple `Review needed` card for both a missing approved location detail and a conflict between two synthetic sources. Use the visible response: `Do not complete this claim. Request / route to the event lead.`

## Teleprompter script

[ON SCREEN: Title card: “Week 2 — Maintain Trustworthy Knowledge”]

Hi, I’m George. A useful context pack is not a bigger folder. It is a working view that helps a person find the approved material for a known question, understand its limits, and know what to do when the answer is not safely available.

[ON SCREEN: Synthetic Context Pack Version 1 outline]

This is a synthetic Context Pack Version 1 for our fictional Northstar volunteer shift-brief workflow. It starts with the scope and human-review boundary. Then it separates the source map, current event facts, operating rules, examples, decisions and exceptions, review-needed items, and the change log.

[ON SCREEN: Select “Current event facts” and show reference-only entry]

Notice that the pack is a working view, not a duplicate archive. For an important fact, I show a safe reference back to the approved source of truth. A permitted reviewer can follow that reference if they need to check the claim. I do not copy a restricted record into a shared page just because it would be convenient for retrieval.

[ON SCREEN: Four operator questions appear]

I build around the questions a real operator asks: What is this pack for? Which source controls this claim? What rule applies? What should I do if something is missing or uncertain? Labels and retrieval cues should make those answers easy to find. If someone has to scan old files or guess whether a prior brief is current, the structure needs work.

[ON SCREEN: Open `Resources/Knowledge Update and Access Policy Template.md`]

Structure only stays useful if someone maintains it. This policy template separates four roles. The source owner is accountable for a particular policy, record, or reference. The pack owner keeps the working view and source links usable. The operational reviewer checks the output in the workflow. The backup escalation owner is the route when the usual owner is unavailable.

[ON SCREEN: Highlight “Current / Pending review / Superseded / Expired / Retired / Unknown”]

Status labels are not decoration. They change what the workflow may do. Current approved material can support the bounded task. Pending review material is a candidate, not active authority. Superseded or expired material should leave the active retrieval path. And if the status is unknown, the operator pauses rather than assuming the source is current.

[ON SCREEN: Synthetic temporary rain-plan decision; status changes to Expired]

Here is a synthetic temporary rain-plan decision. It applied only to a particular event and ended on a stated date. When that date passes, I mark it Expired and remove it from the active path. I may retain it according to the organization’s records practice, but it cannot quietly influence a new brief.

[ON SCREEN: Synthetic safety-procedure update: Pending review → approval → “retest needed”]

Now a proposed safety-procedure update arrives. Even if it looks official, it stays Pending review until the safety lead confirms its authority, effective status, and access boundary. Once approved, the change record notes what changed, why, who approved it, when it takes effect, and what needs retesting. A source update does not automatically prove that the workflow will retrieve or apply it as intended.

[ON SCREEN: Access matrix row]

This access matrix makes permission boundaries visible. In this fictional case, the coordinator may view and run the approved current-event facts for the task. The event lead edits the source and approves a change or final sharing of the brief. The pack records the approved location. But it is important to say this clearly: a written matrix does not grant access. The approved environment and organization process enforce permission.

[ON SCREEN: Split screen: “Needed for task” / “Not needed for task”]

I use data minimization at every stage. The coordinator might need the event time and the approved role instructions. They do not need private contact data or unrelated volunteer records in the active pack. If an authorized person needs to verify a restricted fact, the workflow routes to that person. I do not turn a limitation into a request to paste confidential data into a prompt, a template, or a course discussion.

[ON SCREEN: Review needed: missing location detail]

Let’s look at a missing-context route. The approved location detail is absent. The pack should not fill it from a prior example or memory. It should show: “Do not complete this claim. Request confirmation from the event lead.” A lower-risk draft may leave the field blank and make the review point obvious, but it should not become a final commitment.

[ON SCREEN: Review needed: source conflict]

For conflict, I preserve both source references, identify the specific disagreement, and use the authority order only if it truly resolves the case. If it does not, the responsible owner decides. The system can organize the disagreement. It does not invent a policy interpretation or choose a consequential outcome.

[ON SCREEN: Triggers: policy change, owner change, failed test, scheduled review]

Maintenance is driven by real triggers: a policy change, an owner change, a new approved decision, a failed grounding test, a recurring question, or a scheduled review. If the owner is unavailable and the change is consequential, we restrict or pause the affected workflow. We do not make stale information permanent because it is handy.

[ON SCREEN: Week 2 action list]

This week, build the smallest structure that makes the common path and the stop path usable. Name owners. Make status visible. Define when items expire. Define who may view, run, edit, approve, and share. Then give missing, stale, conflicting, and access-limited context an honest route to a human. That is what makes a first context pack maintainable rather than merely well organized.
