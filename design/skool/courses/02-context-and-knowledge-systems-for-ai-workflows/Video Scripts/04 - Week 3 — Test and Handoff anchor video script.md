# Week 3: Test grounding, document limits, and hand off responsibly

**Embed on:** `Week 3 — Test and Handoff/01 - Assemble the first context pack.md`

**Estimated recording time:** 9–10 minutes

**Outcome:** Members will assemble a reviewable Context Pack Version 1, run safe grounding and retrieval tests for both common and failure cases, make one bounded revision, and hand off the system with limits, access boundaries, ownership, and a next review date.

## What to demonstrate on screen

Use only the **Northstar Neighborhood Center volunteer shift-brief workflow — SYNTHETIC TRAINING EXAMPLE.** All test questions, source titles, roles, and outputs must be fictional. Do not test with real personal, operational, client, member, or confidential information.

1. Show a synthetic `Context Pack Version 1` overview: purpose and scope; source map; fact/rule/example/decision references; access boundary; missing-context playbook; intake and maintenance links; human-review point; version date and pack owner.
2. Open `Resources/Grounding and Missing Context Test Template.md`. Show one synthetic common-path test and its expected controlling source, expected output behavior, claim references, grounding checks, human reviewer, and bounded retest field.
3. Run a safe test question: “Draft the shift-brief opening using `Northstar Event Schedule v2.1 — synthetic` and `Volunteer Safety Procedure v4 — synthetic`.” Show a synthetic draft with two source references. Explain that a reviewer still checks source selection, fidelity, currency, access, and the output before use.
4. Show five concise negative tests in the template: missing location detail → request/event-lead route; conflict between schedule and old planning notes → preserve references and route; stale source → reject or hold pending owner review; request for restricted emergency contact → stop and authorized-reviewer handoff; and an out-of-scope consequential-decision request → decline and route to the qualified human owner. Together with the common-path test, this produces six demonstrated tests. Include one `Revise` outcome and a bounded revision such as moving the authority cue nearer the draft field.
5. Open `Resources/Context System Handoff Template.md`. Show scope, exclusions, active-source status, authority and traceability rule, run/review sequence, access boundary, limitations, escalation routes, maintenance process, safe walkthrough, and next review date.
6. Demonstrate a synthetic receiving-operator walkthrough: locate the controlling source, identify the example-only item, trace one claim, explain the missing-context route, and name the event lead as final reviewer.

## Teleprompter script

[ON SCREEN: Title card: “Week 3 — Test and Handoff”]

Hi, I’m George. By now, you have the pieces of a first context system: a bounded use case, source map, structure, authority rules, maintenance policy, and access boundary. This week, we do not declare it finished because it looks organized. We test what it retrieves, what it claims, how it handles uncertainty, and whether another person can use it without guessing.

[ON SCREEN: Synthetic Context Pack Version 1 overview]

Here is the fictional Northstar Context Pack Version 1. It says what the pack supports, who uses it, who owns it, where the approved sources live, and where human review happens. It separates fact references, operating rules, examples, decisions, and Review Needed items. It also links to the intake and maintenance process.

[ON SCREEN: Highlight “limited scope” and “human review required”]

This is a first version for one bounded workflow. It is not a general expert system, and it does not transfer judgment to AI. Its purpose is to help a coordinator prepare a draft shift brief from approved context. The event lead remains responsible for checking material claims and approving the result.

[ON SCREEN: Open `Resources/Grounding and Missing Context Test Template.md`]

The test template helps us ask specific questions instead of asking, “Does it work?” Each record names the safe test input, expected controlling source or expected stop condition, expected output behavior, reviewer, and the checks we will use before we see the result.

[ON SCREEN: Synthetic common-path test record]

Here is a common-path test. The fictional question is: “Draft the shift-brief opening using Northstar Event Schedule version 2.1 and Volunteer Safety Procedure version 4.” Before I run it, I expect the schedule to support the event time and the procedure to support the safety instruction. I expect the draft to include traceable references. I also expect the event lead to review it before it is used.

[ON SCREEN: Synthetic draft with two labeled claims and references]

The test draft has a shift-time claim with a schedule reference and a safety reminder with a procedure reference. That looks promising, but a fluent draft is not a pass by itself. I check whether it selected the controlling source, whether the claims actually reflect the supplied source, whether the sources are current enough, whether the references are traceable, and whether the output stays inside the access and task boundaries.

[ON SCREEN: Grounding checks; pause on “Human-review route followed”]

Grounding means important claims have support from the approved source for that claim. Retrieval means the operator or workflow can find that source through the pack’s structure and cues. Neither test proves that every future output will be correct. It gives us evidence about this pack version and this test case, which a permitted human reviewer still needs to inspect.

[ON SCREEN: Missing-location test record]

Now we test the failure paths. In this fictional missing-location test, the required approved location detail is not available. The expected behavior is not to borrow a location from an old example. The draft should say what is missing, leave the claim incomplete, and request confirmation from the event lead.

[ON SCREEN: Synthetic output: “Location: Not provided — event-lead confirmation required before distribution.”]

That is useful behavior. It makes the gap actionable and keeps an unsupported statement from turning into a commitment.

[ON SCREEN: Conflict test: Schedule v2.1 versus Planning Notes v1.8]

In the conflict test, current schedule version 2.1 and old planning notes version 1.8 disagree. The test should preserve both references and follow the declared authority order. If the schedule’s current status cannot be confirmed, the output must say that the conflict requires an event-lead decision. The system can describe the disagreement; it should not settle it by wording, file name, or confidence.

[ON SCREEN: Stale-source test: expired schedule reference; “Hold pending owner review”]

In the stale-source test, the workflow receives an expired schedule reference. The expected behavior is to identify the stale status, avoid using it as current authority, and route the source to the owner for confirmation or replacement.

[ON SCREEN: Access-limited test: request for restricted emergency contact; “Stop and route”]

In the access-limited test, the coordinator asks for a restricted emergency contact. The pass condition is a stop and handoff to an authorized reviewer. We do not seek a workaround, reveal the record, or turn the test into a reason to paste confidential data somewhere new.

[ON SCREEN: Out-of-scope test: request to make a volunteer eligibility decision; “Decline and route to qualified human owner”]

The final boundary test asks the workflow to make a consequential decision outside its role. The pass condition is to decline that decision, preserve only the approved context, and route it to the person authorized and qualified to decide. A context pack can organize information; it does not inherit decision authority.

[ON SCREEN: Test result marked Revise; bounded revision: “Move current-source cue next to shift-time field”; retest]

Failures are evidence. Suppose the test finds that the workflow retrieved the old planning notes before the current schedule. I do not change five things at once and call the result better. I make one bounded revision—here, I move the current-source cue next to the shift-time field—record the reason and owner, then rerun the relevant test. That gives the next reviewer a visible trail.

[ON SCREEN: Open `Resources/Context System Handoff Template.md`]

Once the first pack has been tested, we hand it off honestly. This handoff template starts with scope and exclusions. It points to current approved sources and their status without copying restricted contents. It identifies owners, the human-review boundary, access and sharing limits, known limitations, missing and conflict routes, update triggers, and the next review date.

[ON SCREEN: Highlight “What this pack does not support” and “Known limitations and failure modes”]

Do not bury limitations. State what the pack does not support: it does not invent facts, treat examples as current rules, use expired material, disclose restricted information, or make final decisions reserved for accountable people. If the pack has an unresolved source gap, say so. A limitation that the next operator can see is safer than a polished claim that the system is complete.

[ON SCREEN: Synthetic receiving-operator walkthrough]

A good handoff includes a safe walkthrough. I ask the receiving operator to locate the controlling source, identify the example-only item, trace one important claim, explain what happens when required context is missing, and name the person who approves the final brief. In this synthetic case, they identify the event lead. If they cannot find one of those answers without guessing, I revise the pack or handoff before broader use.

[ON SCREEN: Final handoff record: version, recipient role, limitations, next review date]

Record the handoff version, date, receiving roles, accepted responsibilities, open issues, and next review date. A handoff does not grant access or transfer decisions that another qualified role must retain. If ownership, source authority, or permission remains unresolved, restrict use to supervised review or pause the workflow.

[ON SCREEN: Closing: Test → revise one thing → hand off with limits]

Your finish line is a reviewable first system, not a claim of permanent correctness. Run safe tests. Preserve what failed. Make a bounded revision. Then hand off the pack so the next person knows the scope, sources, boundaries, reviewer, and stop route. That is how a context system becomes useful without pretending it can answer everything.

## Member action

1. Complete `Week 3 — Test and Handoff/01 - Assemble the first context pack.md` and assemble Context Pack Version 1 with an overview, source map, classifications, authority rule, access boundary, maintenance route, missing-context route, and human-review point.

3. Make and log one bounded revision for a meaningful test failure; rerun the relevant test. Do not treat a polished response as proof of grounding.
4. Copy `Resources/Context System Handoff Template.md`, complete the handoff, and run a safe orientation walkthrough with the receiving role or a stand-in reviewer.
5. Keep all test and handoff examples authorized, minimized, or clearly synthetic. Never include real confidential data.
