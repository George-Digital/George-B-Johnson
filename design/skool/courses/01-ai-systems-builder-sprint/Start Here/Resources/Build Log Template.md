# Build Log Thread Template

> Copy this into one new Builders Lab community thread. Keep all sprint updates in this same thread so the group can see the decisions, evidence, failures, and revisions in sequence. Remove or replace confidential details before posting.

## Thread title

```text
Build Log: [system name] for [specific user]
```

## Opening post — paste and complete

```text
I’m building: [system name]

Domain: [domain where I have firsthand knowledge]
Specific user: [one role in one situation]
Repeated pain: [task or handoff that keeps causing delay, rework, errors, or uncertainty]

For [user], this system takes [input/problem] and produces [useful output] so they can [next action].

Four-week finish line: By [date], I will show [one usable workflow/output], test it on [number] real or realistic safe inputs, review it with [quality method], and document [next improvement list or revision evidence].

Common path included: [the first workflow path]
Out of scope for this sprint: [features, users, integrations, or edge cases I am deliberately not building]

First artifact: [link, pasted excerpt, sketch, checklist, prompt, sample output, or date I will share it]

My first decision question: [one specific question someone can answer by inspecting the artifact]

Next test: [the smallest test I will run and when]
```

## Update template — use for every meaningful change

```text
## Update — [date]: [short decision or test title]

What I changed:
[Describe the artifact, rule, prompt, workflow step, or assumption that changed.]

What I tested:
[Name the input, scenario, or person. Use a safe/anonymized summary when needed.]

Evidence I got:
[State what happened. Include a link, excerpt, screenshot, checklist result, or observation.]

What worked:
[Be specific.]

What broke or remains unclear:
[Name the failure, missing rule, ambiguity, or risk.]

My next test:
[One smallest next action and a date or condition.]

Decision question for the group:
[Ask one answerable question. Include the relevant artifact or excerpt.]
```

## Feedback request template

Use this when you need critique instead of a general reaction.

```text
Artifact for review: [link or pasted excerpt]
Who it is for: [specific user]
What good should look like: [required outcome or quality standard]
Where it currently fails: [specific issue or uncertainty]
Decision I need help making: [one decision]
What I have already tried: [briefly]
```

## Friday build-log closeout

```text
This week’s artifact: [what now exists]
Evidence: [test result, output, feedback, or observation]
What changed because of evidence: [revision or decision]
What broke: [specific failure or uncertainty]
Next week’s smallest build target: [one artifact or test]
Help I need, if any: [one bounded request]
```

## Useful example

**Title:** `Build Log: Vendor request completeness brief for operations lead`

**Opening line:** “For an operations lead handling vendor requests, this system turns an unstructured email into a completeness brief with missing fields and a draft follow-up, so the lead can request the right information before routing it.”

**Good decision question:** “On this anonymized output, should the missing approval owner appear before delivery date? The lead needs to decide what to chase first.”

## Thread standard

- Post the artifact, not only a description of it.
- State the user and the quality standard before requesting feedback.
- Report failures with enough context to inspect them.
- Ask one decision question at a time.
- Keep the thread current even when progress is slow; an honest blocked update is useful evidence.
- Give useful feedback on another member’s artifact before requesting a second review of your own.
