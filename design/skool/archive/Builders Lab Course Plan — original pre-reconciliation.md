# Builders Lab Course Plan

## Course Name

**AI Systems Builder Sprint**

## Course Description

Skool limit: 500 characters. Current version: 348 characters.

```text
Build one practical AI-powered workflow from your own domain expertise. In this sprint, you’ll choose a real problem, map the workflow, create prompts or AI automation, test outputs, document the system, and share your build for feedback. No hype or one-size-fits-all templates — just practical systems thinking, live examples, and useful critique.
```

## Course Promise

Build and document one practical AI-powered workflow from your own domain expertise.

Builders Lab should create value through practical artifacts, live build examples, critique, and member questions. The course should not overpromise a complete SaaS app, income result, or one-size-fits-all AI course.

## End Deliverable: System Pack

Each member finishes with a simple **System Pack**:

- Problem statement
- Workflow map
- Prompt or AI workflow
- Input/output examples
- Quality checklist
- Simple demo, page, or document
- Next improvement list

## Module 1: Find the Right Problem

**Goal:** Help members avoid vague AI ideas and choose a real problem worth systemizing.

### Lessons

1. Start With a Repeated Pain, Not a Tool
2. Choose a Narrow First Use Case
3. Map the Hidden Workflow
4. Define the Output

### Discussion Prompt

> For [person], this system helps them [job] by [method].

### Member Deliverable

- Narrow use case
- Before/after workflow map
- Output specification

---

## Module 2: Turn Expertise Into System Logic

**Goal:** Capture the judgment behind the work before adding AI.

### Lessons

1. Extract Your Decision Rules
2. Create the Minimum Useful SOP
3. Inputs, Constraints, and Edge Cases
4. What Good Looks Like

### Discussion Prompt

> What do you check that beginners usually miss?

### Member Deliverable

- Decision-rule list
- Simple SOP
- Input checklist
- Quality rubric

---

## Module 3: Build the First AI Workflow

**Goal:** Create a lightweight AI-assisted workflow without overengineering.

### Lessons

1. Pick the Simplest Build Path
2. Prompt Stack: Role, Context, Task, Output
3. Add Examples So AI Understands Quality
4. Create a Repeatable Runbook

### Discussion Prompt

> Post your prompt and one output. Ask the group what is unclear, weak, or missing.

### Member Deliverable

- First prompt stack
- Example input/output pair
- Runbook draft

---

## Module 4: Package the System

**Goal:** Make the system understandable to someone else.

### Lessons

1. Why Every System Needs a Home
2. Create a Simple Demo, Page, or Doc
3. Design the Feedback Loop
4. Turn Confusion Into Better Instructions

### Discussion Prompt

> Share your headline or demo description. Can a stranger understand the value in 5 seconds?

### Member Deliverable

- Landing page outline, demo page, or documentation page
- Feedback loop design
- Revised explanation

---

## Module 5: Test With Real People

**Goal:** Use real feedback to improve the system.

### Lessons

1. Run a Small Manual Test First
2. Ask Better Feedback Questions
3. Improve From Confusion
4. Decide: Improve, Pause, or Package

### Discussion Prompt

> Where would someone get stuck using your system?

### Member Deliverable

- Test plan
- Feedback questions
- Revision list
- Next-step decision

---

## Module 6: Build in Public Without Hype

**Goal:** Help members share progress in a useful, honest way.

### Lessons

1. The Useful Build Log Format
2. Share Decisions, Not Just Wins
3. Turn Questions Into Content
4. Submit Your System Pack

### Discussion Prompt

> What changed, what broke, and what did you learn this week?

### Member Deliverable

- Weekly build log
- Decision post
- Three content ideas from real questions

# Lightweight Launch Sequence

## Pre-Launch

- Publish a post explaining what Builders Lab is and is not.
- Share a few practical examples of systems, workflows, and build logs.
- Ask early members to comment with their niche and system idea.
- Prepare Module 0 and Module 1 only; do not overbuild the entire course upfront.

## Launch Day

Pin these items:

- Start Here post
- Build log template
- First discussion prompt
- Course roadmap

Ask every member to post:

1. Their domain
2. One repeated problem they see
3. One system they want to build

## First 7 Days

- Release Module 0 and Module 1.
- Run one live or async teardown from George.
- Personally reply to every build log.
- Collect common questions for new micro-lessons.

## Weeks 2-4

- Release one module per week.
- Add short lessons based on actual member questions.
- Feature one or two member builds each week.
- Keep the focus on practical artifacts, not passive watching.

## End of First Month

Host a **System Pack Review** thread and ask:

- What did you build?
- What is still unclear?
- What should George build or explain next?

Use the answers to decide the next mini-course.

---

# Quality Bar

Every course lesson should produce at least one of these:

- A clearer problem
- A better workflow
- A usable prompt
- A visible page or demo
- A feedback request
- A documented decision
- A next improvement

Avoid lessons that are only theory. The value of Builders Lab should come from watching George build, applying the same thinking, and getting useful feedback from other members.
